# 权限与数据范围

Yuxi 使用全局单角色 RBAC。每个用户通过 `users.role` 关联一个 `roles.key`，角色同时保存功能权限 key 与模型、Tool、MCP 资源访问范围；超级管理员拥有不可撤销的全部权限与全部资源旁路。

## 判定模型

受控操作必须同时通过三层检查：

1. 动作权限：使用 `require_permission("resource.action")` 校验当前角色是否允许执行该动作。
2. 资源权限：模型、通用内置 Tool 和 MCP 服务必须属于角色的 `resource_access` 允许集合；`knowledge-base` Skill 的知识库工具不进入 Tool 白名单，继续跟随知识库数据范围。
3. 数据范围：继续校验部门、资源创建者和 `share_config`。拥有动作或资源权限不代表可以操作其他部门或未共享的数据。

知识库的按 ID 更新、删除、文档、图谱和评估接口必须先检查对应动作权限，再通过知识库可访问性检查。Agent 与 Skill 同样保留创建者和共享范围约束。

个人资料、个人工作区和本人 API Key 等自助能力不进入功能权限矩阵，仍按登录用户身份隔离；但通过 JWT 或 API Key 发起的模型、Tool、MCP 调用始终继承绑定用户当前角色的资源权限。

## 资源权限

每类资源使用 `all`、`selected`、`none` 三态配置。`selected` 模式只允许显式列出的稳定标识：模型使用 `provider_id:model_id`，内置 Tool 使用工具 `slug`，MCP 使用服务 `slug`。超级管理员始终按 `all` 处理；历史角色升级时保持 `all`，新建自定义角色默认 `none`。

资源权限必须在选择列表、配置保存和实际运行三个边界重复执行。共享 Agent 按实际调用者判断；角色降权后，旧 Agent 配置、恢复任务和已排队任务不得继续使用被收回的资源。Skill 只有在其直接与传递 Tool/MCP 依赖全部获准时才会保留在本次运行上下文中；不可用 Skill 会被跳过，不阻断 Agent 的其余能力，也不得借此扩张 Tool/MCP 权限。`list_kbs`、`query_kb`、`find_kb_document`、`open_kb_document`、`get_mindmap`、`search_file` 除外，它们由知识库功能权限、部门/共享范围和会话启用范围共同约束。

受限角色可为 `chat`、`embedding`、`rerank` 分别指定角色默认模型。显式模型、Agent 配置模型和角色默认模型都必须通过同一授权服务；不允许静默替换越权模型或裁剪越权工具。

## 角色约束

- `superadmin`：系统角色，权限不可修改，始终拥有权限目录中的所有能力。
- `admin`、`user`：系统角色，key 和角色名称受保护、不可删除，权限集合可由超级管理员调整。
- 自定义角色：创建时默认无功能权限、无模型、Tool 或 MCP 资源权限；被有效用户引用时不可删除。
- 角色 key 创建后不可修改，每个用户只允许绑定一个角色。

权限目录的唯一来源是 `yuxi.services.permission_service`。新增受控能力时，先在目录中增加权限 key，再使用统一依赖保护后端接口，并同步前端的菜单、路由、页签和操作按钮。不要新增字符串角色判断来表达功能权限。

## 组织架构与管理范围

部门是多根组织森林。每个根节点代表一个独立主体；系统默认部门是额外的保留根节点，不能移动、停用或删除。普通节点只能在同一主体内移动，同一上级下名称唯一，界面和接口使用完整路径区分不同分支的同名部门。

每个用户必须有且仅有一个主部门，可同时属于同一主体下的多个兼职部门。默认部门用户不能兼职到其他主体，用户也不能跨主体兼职。主、兼职关系只表达人员隶属，不自动产生管理能力。

组织管理范围由超级管理员显式配置。一个管理节点覆盖自身及全部有效后代，多个节点取并集；用户自身属于哪个部门不限制其管理授权。执行用户或部门操作时，必须同时具备对应 RBAC 动作权限和目标节点的组织管理范围。

节点停用前必须先迁移直属成员，并停用或迁移启用中的直属子节点。停用节点不会继续产生新的组织管理或资源继承权限，但历史成员、授权和路径记录会保留。

## 资源的组织继承

知识库、Agent 和 Skill 的 v2 共享配置统一使用以下规则：

1. `department_ids` 中的节点向全部有效后代继承。
2. `excluded_department_ids` 中的节点阻断其整棵子树，不能在被排除子树内重新包含下级节点。
3. `user_uids` 是指定用户例外，优先于部门排除。
4. 用户从主部门与全部兼职部门获得的权限取并集；一条成员路径被排除，不影响另一条允许路径。
5. 未带 `org_scope_version: 2` 的历史配置继续按精确部门 ID 判断，升级不会自动扩大原有资源范围。

Agent 分别保存使用范围和管理范围。命中使用范围只能调用 Agent；命中管理范围且具备 `agents.update` 才能编辑配置。管理范围不授予删除能力，删除仍只允许所有者或超级管理员，并继续叠加 `agents.delete` 动作权限。

## 生效与审计

JWT 和 API Key 只负责定位用户；每次请求都会从数据库读取该用户当前角色的功能权限与资源权限，因此修改角色权限或用户角色后立即生效。角色创建、权限修改、角色分配和删除会写入操作日志，其中权限修改同时记录功能权限和资源授权的前后差异。
